# 顶层设计：因子挖掘框架的分层与契约

> 项目长出了多个**因子生成器**（GP、RL，未来 LLM）。本文钉死框架的分层、依赖规矩与两条契约，
> 保证「加第 N 个生成器也不会乱」。是新增生成器 / 重构前必读的北极星。

## 一句话架构

**生成（generators）→ 表示与求值（core）→ 评估与筛选（consumers）**，三层之间靠**两条契约**解耦：

1. **因子的统一表示 = `Node`**（表达式树，[`src/core/tree.py`](../src/core/tree.py)）。任何生成器的产物都是 `Node`。
2. **生成器的统一产出 = `factor_library` schema**（落盘 pkl）。任何消费者只认这个格式。

满足这两条，生成器就是可插拔的平级插件，消费者一律 generator-agnostic。

## 分层与依赖图

```text
   ┌──────────────────────────────────────────────────────────┐
   │  generators/   gp/      rl/      (llm/ 未来)               │  生成器：产出 Node 因子
   │                ▲ 平级，互不依赖；只依赖 core + data         │  → 落盘 factor_library
   └────────────────┼─────────────────────────────────────────┘
                    │ 依赖
   ┌────────────────▼─────────────────────────────────────────┐
   │  core/    tree(Node) · operators · evaluator              │  因子的「表示 + 求值」
   │           中立核：不依赖任何生成器，也不依赖消费者          │  Node → 因子矩阵
   └────────────────▲─────────────────────────────────────────┘
                    │ 依赖（evaluate）          ┌── factor_library.pkl ──┐
   ┌────────────────┴───────────────────────────▼──────────────┐
   │  consumers   evaluation/(IC·ICIR·fitness) · backtest/      │  消费因子：评/验/测/选
   │              · significance · deflated · screen · synthesis│  只读 library schema + core
   └──────────────────────────────────────────────────────────┘
        ▲
   ┌────┴─────────────────────────────────────────────────────┐
   │  data/   loader · preprocess（to_wide / to_panel）         │  行情获取与整形（底座）
   └──────────────────────────────────────────────────────────┘
```

**依赖铁律**

- 生成器 **只能** import `src.core` + `src.data`；**永远不 import 另一个生成器**。
- 消费者 **只能** 依赖 `src.core`（拿 `evaluate`）+ `factor_library` schema；**不认识任何具体生成器**。
- `core` 不依赖 src 内任何东西（纯表示+求值），`data` 只依赖外部接口。

依赖永远**向下/向心**，不允许横向（生成器↔生成器）或向上（core→生成器）。

## 两条契约的细节

### 契约一：因子 = `Node`

[`src/core/tree.py`](../src/core/tree.py) 的 `Node`（name / arity / children / value / out_type）是因子的唯一表示。

- GP 直接长 `Node` 树；RL 把 RPN token 序列 `rpn_to_node` 成 `Node`；LLM 把文本 parse 成 `Node`。
- 无论谁生成，[`src/core/evaluator.py`](../src/core/evaluator.py) 的 `evaluate(node, wide)` 都能求值成因子矩阵——**这是所有生成器复用同一套求值/IC/回测的根本原因**。

### 契约二：生成器产出 = `factor_library` schema

```python
{
    "config_path": str,          # 用的哪个 config（复现用）
    "split": str,                # train/test 分界（regime 断点教训：训练段须 2021+）
    "factors": [
        {"expr": str, "tree": Node, "size": int,
         "train_ic": float, "test_ic": float},   # mean rank IC，签名带方向
        ...
    ],
}
```

- 生成器跑完落盘这个 pkl（因子动物园、RL 已是；GP-walkforward 是历史遗留的 `{folds, picks}` 旧格式，**待统一**）。
- 消费者一律读它：[`screen_factors.py`](../scripts/screen_factors.py)（按 train IC 选 + 回测）、[`deflated.py`](../scripts/deflated.py)（选择偏差盖章）、[`synthesize.py`](../scripts/synthesize.py)（多因子合成）。
- **正因为这层契约，换生成器只换上半截，下半截验证/筛选零改动。**

## 文件归属（重构后）

| 层 | 包/文件 | 角色 |
| --- | --- | --- |
| **core** | `src/core/{tree,operators,evaluator}.py` | 因子表示 + 算子注册表 + 求值器（中立核） |
| **generators** | `src/gp/{engine,nsga2,stgp}.py` | GP 生成器：随机树/遗传算子/NSGA-II/强类型 |
| | `src/rl/{tokens,env,policy,train_rl}.py` | RL 生成器：词表/MDP 环境/GRU 策略/REINFORCE |
| | `src/llm/`（未来） | LLM 辅助生成 |
| **consumers** | `src/evaluation/{metrics,fitness}.py` | IC/ICIR/分组 + 适应度 |
| | `src/backtest/simple.py` | 涨跌停/T+1 现实回测 |
| | `scripts/{screen_factors,significance,deflated,synthesize}.py` | 筛选 / 显著性 / deflated / 合成 |
| **data** | `src/data/{loader,preprocess}.py` | 行情获取 + `to_wide`/`to_panel` |
| **utils** | `src/utils/logger.py` | 实验日志 |

> 注：`gp/` 与 `rl/` 物理上直接在 `src/` 下（非 `src/generators/` 子目录）。逻辑上它们是平级生成器；要不要再套一层 `generators/` 目录是可选项，**当前不做**（避免又一次大范围改 import，过度整理）。

## 怎么加一个新生成器（LLM 实操配方）

照契约长，不碰下半截：

1. 新建 `src/llm/`，**只 import `src.core` + `src.data`**。
2. 生成逻辑随意（prompt LLM → 拿到表达式文本 → parse 成 `Node`）。复用 `core.operators` 的算子名保证可求值。
3. 跑完落盘 `factor_library.pkl`（契约二的 schema）：对每个因子算 `train_ic`/`test_ic`（训练段 2021+）。
4. 完事——`screen_factors / deflated / synthesize / backtest` 直接吃它的产出，**一行下游代码都不用改**。

唯一硬约束：**产物必须是合法 `Node`（能被 `evaluate` 求值）+ 落盘必须是 `factor_library` schema**。守住这两条，框架就不会乱。

## 刻意不做（避免过度设计）

- **不写 `Generator(ABC)` 抽象基类 + 注册表**：两个半生成器还不到需要框架的程度（rule of three）。契约用「文档约定 + schema」表达即可，不用代码强制。等真有第三、四个生成器、且确实痛了再抽。
- **不强行统一 walkforward 的旧 schema**：标记为待清理，不阻塞主线。
- **不提前上 `src/generators/` 子目录**：纯属重命名，收益低、改动面大。
